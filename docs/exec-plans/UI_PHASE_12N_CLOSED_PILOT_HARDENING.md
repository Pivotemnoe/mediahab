# UI Phase 12N — Closed-pilot hardening and release

## Status

Local implementation and the complete pre-release gate passed on 2026-08-14. GitHub checks, production backup, application-only rollout, and post-release verification remain before the phase can be marked released.

## Goal

Turn the locally accepted first-run cleanup into an honest closed-pilot release:

`owner creates one-time invite -> tester registers once -> first-run tour -> voice/notebook workflow -> manual review/export -> recoverable owner-assisted access`

No production switch occurs until the complete local gate, GitHub source gate, fresh backup, migration preflight, and application-only rollout checks pass.

## Scope and product decisions

- Public self-registration is closed in production. Registration requires a one-time, email-bound, expiring pilot invitation generated by a server-side operator command.
- Possession of an owner-delivered invite is the closed-pilot email proof. The invited account is marked verified when the matching one-time token is consumed.
- Password recovery is honest and owner-assisted until SMTP credentials and an approved sender are configured. A server-side command generates a one-time reset link; the public recovery page directs the tester to the named support contact instead of promising an email that is not sent.
- Registration records explicit acceptance of the closed-test terms and data notice in the audit log.
- Every frontend service in `api` mode fails closed with real empty/error state. Fixture data remains available only in explicit fixture mode.
- Unfinished publication, integration, calendar, workspace, and billing surfaces are not pilot navigation. Direct visits show one plain-language unavailable surface rather than internal phase names, provider data, tokens, or mock controls.
- The standalone Ideas implementation remains in code for evaluation, but the backend capability is disabled. Until its repetition gate passes, Ideas is absent from pilot navigation, onboarding, marketing claims, the composer, and quick actions; a direct visit explains that it is unavailable without showing a misleading quota.
- The first-run tour has three truthful steps: create a project and publication, save a notebook note, and add style examples. It never promises an action that the current pilot cannot complete.
- Remove request IDs, queue diagnostics, data-mode badges, raw service messages, technical storage wording, duplicate project controls, and redundant progress counters from tester-facing surfaces. Diagnostics and accounting remain in logs and durable records.
- Production publication execution uses PostgreSQL outbox plus Celery worker. The API commits queued work and returns; a periodic worker drains due events. Inline processing remains a test/local compatibility mode only.
- API and worker containers run as an unprivileged `app` user; web runs as the image `node` user.
- Production readiness checks the database, Redis, and exact Alembic head and returns `503` when any dependency is unavailable or the schema is behind.
- Existing users, workspaces, content, revisions, media, publications, usage, sessions, and connector records are preserved.

## Data and migration

- Add `pilot_access_invites` with normalized email, hashed token, expiry, consumption time, optional creator, and timestamps.
- Never store a raw invite or password-reset token.
- Migration upgrade creates only the new table and indexes.
- Downgrade is allowed only when no invite rows exist; otherwise it stops to preserve audit evidence.

## Access tooling

- Add an operator-only CLI for creating pilot invitations and password-reset links.
- The CLI reads the protected server `DATABASE_URL`; it is not an HTTP admin endpoint.
- Links are printed once to the operator terminal and must not enter application logs, Git, screenshots, or chat.

## Publication worker

- Move the Celery package to a non-conflicting `worker_app` namespace so it can import the API domain package.
- Add a periodic task that requeues stale locks and drains due `publication.publish` outbox events in bounded batches.
- Add row locking with `SKIP LOCKED` for multi-worker safety.
- API `publish-now` and retry use `PUBLICATION_EXECUTION_MODE`; production is `worker`, local/tests may use `inline`.

## Acceptance tests

- Closed registration rejects requests without an invite.
- An invite works only for its normalized email, before expiry, and only once.
- Registration requires both pilot consent fields and marks the invited user verified.
- Verify-email and reset-password pages call their real API endpoints and show human success/errors.
- Personal reset and verification tokens remain hidden in their links/forms; opening those pages without a valid link shows a plain request-for-help state rather than a technical code field.
- Owner-assisted reset CLI creates a valid one-time link; reset revokes active sessions.
- API mode contains no fixture fallback on dashboard, content, projects, style/examples, publications, integrations, billing, workspace, media, or calendar services.
- Direct pilot-disabled routes expose no phase/API/provider/token/mock implementation text.
- Worker mode returns `queued`; the worker processes a due outbox event idempotently and recovers a stale lock.
- Existing Phase 12K/12L/12M, notebook, guided forms, platform limits, connector, auth, publication, and hidden-Ideas implementation tests remain green.
- Mobile and desktop browser acceptance covers invitation registration, login, tour skip/replay, composer, notebook, account, direct-route gate, terms, and privacy.

## Risks and rollback

- Closed registration can strand a tester if an invite expires. Generate a new invite; never reactivate the raw token.
- A worker-mode release can leave publications queued if Celery is unhealthy. Readiness and worker logs are release gates; rollback restores the previous API/worker/web images while keeping outbox rows intact.
- The new table is additive. Application rollback can leave it unused; no destructive downgrade is required.
- Legal/operator identity may need a later formal document. The pilot notices remain factual and explicitly limited to testing.
- Real iPhone background/sleep behavior still requires a physical-device acceptance pass; browser automation cannot substitute for it.
