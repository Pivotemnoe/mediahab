## Цель

Реализовать настоящую цепочку клиента:

`публичная главная -> регистрация/вход -> личный кабинет -> один или несколько проектов/каналов -> общие правила и одобренные примеры -> при желании правила/примеры рубрики -> диктовка -> проверка расшифровки -> сборка версий площадок -> реальная история`

Новый владелец должен попадать в настоящий личный кабинет, а не в пустой composer или принудительный мастер настройки. Проект обязателен только перед первой сохраняемой публикацией; пользовательская рубрика необязательна. Проекты, правила, примеры и необязательные рубрики сохраняются через существующий версионируемый backend API и остаются доступны со страниц проекта.

## Реализация

- Публичная главная остаётся объяснением продукта и основным входом в регистрацию.
- `/app` становится настоящим личным кабинетом с проектами/каналами, последними реальными материалами и понятным первым действием.
- Пользователь может создать несколько проектов/каналов в пределах тарифа, который возвращает backend.
- Превратить `/app/projects/new` из макета в рабочую русскую форму с CSRF-защищённым сохранением через API.
- В форме проекта задать общие правила канала: аудитория, голос, тон, структура, обязательные ориентиры, запрещённые элементы и CTA.
- После создания проекта дать три явных продолжения: открыть канал, добавить идеальные примеры или сразу начать диктовку без рубрики.
- Превратить `/app/projects/{projectId}/rubrics/new` в рабочую форму: название, цель, исходные факты, желаемая длина, тон, структура, обязательные и запрещённые элементы, площадки по умолчанию.
- Необязательную рубрику сохранять через существующий versioned API. Источник сделать `voice_or_long_text`, чтобы запись Phase 12A работала сразу.
- Обычные посты без пользовательской рубрики поддержать через versioned-профиль общих правил проекта. Не показывать его в списке рубрик; в composer писать `Без рубрики — общие правила проекта`.
- Добавить рабочую форму примеров проекта: несколько идеальных публикаций за один раз, с необязательной привязкой к рубрике. Общие примеры действуют на весь канал, рубричные имеют приоритет внутри рубрики.
- После проекта или необязательной рубрики оставлять пользователя в понятном маршруте проекта и показывать явное действие `Создать публикацию`; composer загружает сохранённый проект и включает микрофон.
- Оставить создание проекта, правила, примеры и рубрики доступными из кабинета и страниц проекта.
- Не импортировать и не хардкодить предметный проект-пресет.
- В API-режиме «История» показывает только реальные материалы текущего workspace. Пустое состояние и ошибка API никогда не подменяются fixture-карточками или демо-студией.

## Данные и миграции

Миграция не нужна, если общие правила проекта представлены существующими versioned-таблицами рубрики и input schema, но скрыты из пользовательского списка рубрик. Существующие данные и Docker volumes не затрагиваются.

Локальная приёмка создала только синтетический тестовый аккаунт, два проекта, одну необязательную рубрику, три одобренных примера и два тестовых материала в локальном PostgreSQL MediaHub. Production-приёмка добавила одного явно помеченного синтетического владельца `example.test`, один проект, один одобренный пример и один тестовый материал. Реальная почта и редакционные данные не использовались. PostgreSQL, Redis, Docker volumes, object storage, Caddy и соседние сервисы не пересоздавались и не менялись при app-only переключении.

## Проверка

- Пустой workspace после регистрации открывает настоящий пустой кабинет без демо-проекта и демо-материалов.
- Отправка формы создаёт versioned-проект и предлагает сразу диктовать либо добавить необязательную рубрику.
- Можно создать несколько проектов, пока это разрешает entitlement workspace.
- Общие правила проекта попадают в версионируемый контекст ИИ.
- Из UI можно импортировать и одобрить несколько общих или рубричных идеальных публикаций.
- Диктовка без рубрики создаёт материал по versioned-профилю общих правил проекта.
- Отправка необязательной рубрики создаёт активную versioned-рубрику и ведёт в голосовой composer.
- История нового workspace пуста, содержит только реальные материалы и не показывает fixtures в API-режиме.
- Недоступный материал показывает состояние «не найден», а не демо-студию.
- Ошибки валидации и API остаются на форме и показываются по-русски без подмены демо-данными.
- Существующие тесты проекта, рубрики, auth, voice, AI и публикаций продолжают проходить.
- Выполнить lint, typecheck, production build web, общие тесты, тесты API и `git diff --check`.

## Риски

- Количество проектов контролируется entitlement backend; при превышении лимита нужно показать понятную ошибку, а не заменять данные.
- Внутренний профиль общих правил проекта не должен выглядеть как пользовательская рубрика или мешать обычной работе с рубриками.
- У первой рубрики пока нет одобренных примеров; генерация обязана сохранять факты и не обещать стиль на основе примеров.
